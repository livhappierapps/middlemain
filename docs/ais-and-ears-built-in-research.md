# AIs & Ears built-in feature: research before implementation

**Status:** Research only; no application code changed.  
**Repository reviewed:** `livhappierapps/AIsandEars` (`main`, source cloned read-only).  
**Question:** What does the existing phone-to-service pipeline actually send and receive, where does inference happen, and what explains a stable-looking connection with no useful camera/audio result?

## What the current pipeline does

**Audio is a WebSocket stream; camera is not.**

1. **Session creation.** Middlemain sends `POST {configured-domain}/api/bridge/session` with the shared bridge `apiKey`, tier, and requested session duration. The AIs & Ears API validates that key against `BRIDGE_API_KEY`, creates a session record, and returns `sessionId`, `wsUrl`, and `visionUrl`. The session route defaults to a 30-minute `full-session`, allows up to 480 minutes, and does not create a per-user daily usage record. Sources: `artifacts/middlemain/context/AisAndEarsContext.tsx:310-357`; AIs & Ears `artifacts/api-server/src/routes/bridge.ts:39-116`.
2. **Microphone.** Middlemain records a WAV chunk, validates its actual RIFF/WAVE format, extracts PCM16 mono 24 kHz samples, base64-encodes those samples, and sends `input_audio_buffer.append` over the WebSocket. AIs & Ears proxies these events to xAI Realtime. xAI runs server-side voice activity detection and speech/conversation inference; its text/transcript events return through the proxy. Sources: Middlemain `artifacts/middlemain/context/AisAndEarsContext.tsx:367-429`, `artifacts/middlemain/utils/bridgeAudio.ts:4-43`; AIs & Ears `artifacts/api-server/src/websocket/grokRealtime.ts:35-40,99-140,153-170`.
3. **Camera/screen.** Middlemain captures one JPEG frame, wraps it in a `data:image/jpeg;base64,...` URL, and POSTs it to the session’s `visionUrl`; live mode repeats after each request finishes. AIs & Ears validates the data URL and size, checks the session, then calls xAI’s `https://api.x.ai/v1/chat/completions` with model `grok-2-vision-1212`. It returns JSON `{ message, model }`. Vision inference is at xAI, not on the phone or in the bridge server. This is a separate HTTP request—not a camera stream over the audio socket. Sources: Middlemain `artifacts/middlemain/components/BridgeCameraPreview.tsx:74-115`, `artifacts/middlemain/utils/bridgeVision.ts:22-66`; AIs & Ears `artifacts/api-server/src/routes/grokVision.ts:39-68,71-93,104-160`.
4. **Where the result goes.** Middlemain emits vision replies and audio transcripts to Bridge Terminal lines. Its ordinary chat pane does not receive them automatically. Sources: `artifacts/middlemain/context/AisAndEarsContext.tsx:257-270,359-365`; `artifacts/middlemain/app/(tabs)/terminal.tsx:140-154`.

The standalone AIs & Ears app follows the same split: microphone audio goes through its Realtime WebSocket; a camera snapshot goes to `/api/grok-vision`. Its conversation UI handles text/transcript events and speaks text with Expo Speech; it explicitly ignores returned audio chunks for playback. Sources: AIs & Ears `artifacts/ais-and-ears-native/app/conversation.tsx:4-14,290-352,749-804`.

## Three code-supported failure points

1. **Turning Cam on does not send a picture.** Middlemain’s camera toggle says preview only; sending requires the separate **Send one frame** or **Start live** action and confirmation. A live frame then uses the separate HTTP vision endpoint. A successful session or audio socket does not mean a frame was captured, uploaded, or analyzed. Source: `artifacts/middlemain/context/AisAndEarsContext.tsx:453-460`; `artifacts/middlemain/components/BridgeCameraPreview.tsx:74-130`.
2. **Android’s “WAV” recording may not be PCM audio.** Middlemain’s Android recorder selects `AndroidOutputFormat.DEFAULT` and `AndroidAudioEncoder.DEFAULT`; the filename/extension does not guarantee PCM16. Its validator correctly rejects anything other than PCM16/24 kHz/mono, so a connection can remain open while no audio chunk is accepted. The standalone AIs & Ears native client has the same Android default encoder and strips 44 bytes without validating the encoding. iOS is explicitly configured as linear PCM. Sources: Middlemain `artifacts/middlemain/context/AisAndEarsContext.tsx:77-98`; `artifacts/middlemain/utils/bridgeAudio.ts:4-35`; AIs & Ears `artifacts/ais-and-ears-native/app/conversation.tsx:68-97,382-427`. Middlemain’s existing bug report also calls Android physical-device audio unverified: `docs/final-bug-fix-before-shipping-report.md:62-70`.
3. **“Connected” and visible responses are not end-to-end proof.** Middlemain sets its bridge status to connected after the session-creation HTTP response, before opening the WebSocket. The server sends a separate `connected` event only after xAI’s socket opens, but Middlemain’s handler ignores that event and most response types. It forwards recognized transcript events to Bridge Terminal, does not play returned audio, and does not insert results into the regular chat. A green state can therefore precede media readiness, and a processed response may not appear where a user expects it. Sources: Middlemain `artifacts/middlemain/context/AisAndEarsContext.tsx:243-289,310-357`; AIs & Ears `artifacts/api-server/src/websocket/grokRealtime.ts:105-140`; Middlemain `artifacts/middlemain/app/(tabs)/terminal.tsx:140-154`.

These are source-backed causes and risks, not proof of which exact one caused a particular phone test. The current source should be physically tested on iPhone and Android after any fix.

## Render endpoint and credential boundary

The verified route is **`POST {APP_BASE_URL}/api/bridge/session`**, followed by the returned `wsUrl` and `visionUrl`. The AIs & Ears Render blueprint names a web service `ais-and-ears-api` and declares `APP_BASE_URL` and `BRIDGE_API_KEY` as dashboard-supplied environment values (`render.yaml:1-69`). The repository contains the endpoint path and service name, but **no public Render hostname**; the host cannot be truthfully supplied from this checkout. The service’s configured `APP_BASE_URL` must be checked in Render before a client URL is finalized.

The bridge key is a shared service credential. The route’s own comments say to keep it server-side (`artifacts/api-server/src/routes/bridge.ts:18-22`), yet the current Middlemain client sends it from the phone in the JSON body (`artifacts/middlemain/context/AisAndEarsContext.tsx:328-342`). SecureStore protects a saved value at rest; it does not make a long-lived shared key unextractable from a client app or its requests. The Commander pattern uses an `X-Executive-Key` checked against a server environment value, and its code explicitly says it is owner-only and must never be embedded in a public client (`artifacts/api-server/src/lib/security.ts:4-19`). **Do not put either the Render bridge key or the owner executive key in the public app.** A public implementation needs a server-side proxy holding the service key and an appropriate user entitlement/session boundary.

## Trial, subscription, usage meter, and release gates

- The live audio proxy relays WebSocket payloads; it does not meter or persist provider usage. The vision route returns only `message` and `model`; it does not return usage or dollar cost. Sources: AIs & Ears `artifacts/api-server/src/websocket/grokRealtime.ts:153-170`; `artifacts/api-server/src/routes/grokVision.ts:154-160`. A trustworthy live-dollar ticker therefore needs new server-side usage accounting and a maintained provider price schedule. Until provider usage is measured, the UI must call it an **estimate**, not exact spend.
- The bridge session endpoint accepts a duration and creates a session, but has no seven-day trial state or 30-minute-per-user-per-day enforcement (`artifacts/api-server/src/routes/bridge.ts:48-93`). A daily cap must be enforced by the server and associated with a durable user identity; a client-only timer is bypassable.
- Middlemain’s legal screen currently states that in-app purchases and subscriptions are not enabled (`artifacts/middlemain/app/legal.tsx:81`). A $1.99 subscription and seven-day offer need configured Apple/Google products and entitlement handling. Toggling the feature can open the store purchase flow, but the trial must start only after the user confirms the store sheet; it cannot silently begin a subscription or charge.
- `render.yaml` declares the API service on Render’s free plan and notes that it spins down after inactivity. That is a cold-start/availability risk for a real-time feature, not evidence of the currently deployed plan (`render.yaml:1-8`).

## Recommendation for the approval decision

The repository has a working, two-part capture/inference protocol to adapt, but not a unified “stream” or a public-ready billing/auth layer. If approved, keep the setting off by default; make first use an explicit, store-managed subscription/trial choice; issue short-lived, per-user media sessions through a Middlemain server endpoint; enforce the daily cap server-side; and route confirmed results into the intended chat pane. Do not expose the AIs & Ears shared key or owner-only Commander key in a consumer build. Treat the first implementation as an approximate cost meter unless the provider’s actual usage data can be captured.

**No application code was changed as part of this research.**
